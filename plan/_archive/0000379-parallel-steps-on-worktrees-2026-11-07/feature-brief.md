# Feature Brief - Parallel steps on worktrees

**Feature ID:** 0000379-parallel-steps-on-worktrees

## Business Goal

An initiative takes as long as all its steps added together, because the driver runs one step at a time in one working tree. This feature lets steps that touch different files run at the same time. Each step gets its own worktree, log, and control area. The merge queue from step 2 merges each ready PR in turn.

Backlog entries pulled in: 0000375. Initiative step 3 of 21.

## Scope Boundaries

### In Scope
- `Lane` and `After` columns in `## Steps`, the `**Concurrency:**` field, and the `running` and `ready` statuses, in `initiative.template.md`, the standards, and the active chart.
- A scheduler in `initiative-run.mjs`: ready test, lane rule, concurrency cap, one worktree, log, and control area per step.
- Queue hand-off: a step ends at `ready`, and the driver runs `merge-queue.mjs run` for it. P4 stops bumping versions in an initiative step.
- Stop rules for `Blocked:`, `Question:`, `Restart:`, and `Setup:` across running steps, with a state report.
- `initiative-watch.mjs` and the initiative skill report each running step.
- The `standard-boot.md` worktree rule scoped to human sessions, and this repo's `CLAUDE.md` regenerated by setup.
- I-A Chart coaching of lane and `After`. I-C, I-D, and I-E text for concurrent steps.

- Any change to `merge-guard`.
- Per-step model or turn-cap settings.

## Constraints and Assumptions

### Constraints
- The orchestrator skill has little byte headroom. This step adds no text to it.
- The squash title form is `{feature-id}: {Title} (#{n})` with the 7-digit id.
- Step 3 itself ships under the old driver: it merges through `merge-queue.mjs` run from its own session.

### Assumptions
- `.claude/`, `CLAUDE.md`, and `AGENTS.md` are setup output that git ignores, so the driver copies them into each worktree.
- A step session reads its queue items from the main root, named by `RAVINTIO_INITIATIVE_ROOT`.

## Scenario Paths

**Happy path:** The chart sets `**Concurrency:** 2` and two pending steps in different lanes with no `After`. The driver starts both in worktrees, each ends ready with a PR, and the queue merges them one after the other.

**First-run path:** A chart has no `Lane` or `After` column and no `**Concurrency:**` field. The driver runs it one step at a time as before.

**Error / sad path:** One running step prints `Blocked:`. The driver starts no new step, lets the others reach a safe point, and prints each step's state.

**Cross-session continuity:** Row statuses and the control area survive a driver restart. On start the driver reuses an existing worktree for a `running` row and treats a `ready` row as ready to queue.

## Acceptance Criteria

- [ ] A driver test with two stub steps in different lanes runs both at once and merges both through the queue.
- [ ] Two stub steps in the same lane, or linked by `After`, run one after the other.
- [ ] A `Blocked:` line in one running step stops new starts, and the report names every step's state.
- [ ] `initiative.template.md` holds `Lane` and `After` columns and `**Concurrency:** 3`. A value of 1 runs steps one at a time.
- [ ] The `CLAUDE.md` template allows driver-run worktrees and tells a human session to work on a `feat/` branch in the main tree.
- [ ] The existing driver suites pass unchanged.
